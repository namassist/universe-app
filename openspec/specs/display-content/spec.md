# display-content Specification

## Purpose

What a paired kiosk shows and where it comes from: running texts as records with
a per-device override and a master fallback, sounds as records backed by an
uploaded audio file in explicitly configured storage, the display endpoint that
resolves a calling device's effective content and records its heartbeat, and the
menus that govern writing any of it.

## Requirements

### Requirement: Running texts are persisted records

The system SHALL persist running texts as database records carrying the text, a
colour, and an active flag. The permitted colour values SHALL be defined in the
shared contracts so the database, the API schema, and the client cannot drift.

#### Scenario: Create a running text

- **WHEN** a caller holding `manage` on `running-text` creates a text with a colour
- **THEN** the record SHALL be persisted and SHALL appear in subsequent list responses

#### Scenario: Invalid colour rejected

- **WHEN** a caller creates a running text with a colour outside the defined values
- **THEN** the API SHALL respond 422 and SHALL NOT create the record

#### Scenario: Inactive text is not displayed

- **WHEN** a running text is deactivated
- **THEN** it SHALL be excluded from what any display receives, and SHALL remain listed in its management screen

### Requirement: A display shows its own running texts, falling back to the master list

A display device SHALL be able to carry its own running texts. When a device has
one or more of its own texts, those SHALL be what it displays. When a device has
none, it SHALL display the active master running texts.

#### Scenario: Device with its own texts

- **WHEN** a device that has two of its own running texts requests its display content
- **THEN** the response SHALL contain those two texts and SHALL NOT contain the master texts

#### Scenario: Device with no texts of its own

- **WHEN** a device with no texts of its own requests its display content
- **THEN** the response SHALL contain the active master running texts

#### Scenario: Removing a device's last text restores the fallback

- **WHEN** the last of a device's own running texts is removed
- **THEN** that device SHALL display the active master running texts

#### Scenario: A device's texts are not shown on another device

- **WHEN** one device is configured with its own running texts
- **THEN** no other device's content SHALL contain them

### Requirement: The display endpoint serves effective content to the calling device

`GET /v1/display/:kind` SHALL return the running texts that the calling device
is to display, resolved according to the fallback rule above.

A device session SHALL be permitted to read only the display kind it is
registered for. Reading this endpoint from a device session SHALL record the
device's heartbeat, so a device that has content is by definition one that has
just reported in.

#### Scenario: A paired device receives its content

- **WHEN** a device with a valid device session requests its own display kind
- **THEN** the API SHALL respond 200 with the effective running texts

#### Scenario: Reading records the heartbeat

- **WHEN** a device session reads its display content
- **THEN** the device's last-seen timestamp SHALL be updated and the device SHALL be reported as online

#### Scenario: A device may not read another kind

- **WHEN** a device registered for one display kind requests a different kind
- **THEN** the API SHALL respond 403

#### Scenario: A kiosk polls for content

- **WHEN** a kiosk screen is open
- **THEN** it SHALL request its display content from the API rather than reading static data, and SHALL reflect a change to its running texts without a manual reload

### Requirement: Sounds are persisted records with an uploaded audio file

The system SHALL persist sounds as database records carrying a name, the stored
file's identity, its MIME type, its size in bytes, and an active flag. Creating
a sound SHALL accept an uploaded audio file.

The stored filename SHALL be generated by the system and SHALL NOT be taken from
the client-supplied name.

#### Scenario: Upload a sound

- **WHEN** a caller holding `manage` on `sound` creates a sound with a name and an audio file
- **THEN** the file SHALL be stored, the record SHALL be persisted with its MIME type and size, and the sound SHALL appear in subsequent list responses

#### Scenario: Non-audio file rejected

- **WHEN** a caller uploads a file whose MIME type is not audio
- **THEN** the API SHALL respond 422, SHALL NOT store the file, and SHALL NOT create the record

#### Scenario: Oversized file rejected

- **WHEN** a caller uploads a file larger than the configured maximum
- **THEN** the API SHALL respond 422, SHALL NOT store the file, and SHALL NOT create the record

#### Scenario: Client filename cannot influence the storage path

- **WHEN** a caller uploads a file whose name contains path traversal characters
- **THEN** the stored file SHALL be written under the configured sound directory using a generated name, and no file outside that directory SHALL be created or overwritten

### Requirement: A sound's audio is served by the API

The system SHALL serve a sound's audio file over an endpoint that streams it
from storage without buffering the whole file in application memory.

#### Scenario: Play a sound

- **WHEN** an authorized caller requests a sound's audio
- **THEN** the API SHALL respond 200 with the file's bytes and its stored MIME type

#### Scenario: Unknown sound

- **WHEN** a caller requests audio for a sound that does not exist
- **THEN** the API SHALL respond 404

#### Scenario: Deleting a sound removes its file

- **WHEN** a caller holding `manage` deletes a sound
- **THEN** the record SHALL be removed and its stored file SHALL NOT remain

### Requirement: The sound storage location is explicit configuration

The directory in which sound files are stored SHALL be supplied as explicit
configuration rather than derived from the environment. The API SHALL report at
startup whether that directory is present and writable.

#### Scenario: Startup with a writable directory

- **WHEN** the API starts with the sound directory configured and writable
- **THEN** startup SHALL succeed and the health report SHALL indicate sound storage is available

#### Scenario: Startup with an unwritable directory

- **WHEN** the API starts with a sound directory that is missing or not writable
- **THEN** the condition SHALL be reported at startup rather than surfacing at the first upload

### Requirement: Display content access is governed by its own menus

Running texts SHALL be governed by the `running-text` menu and sounds by the
`sound` menu, each requiring `view` to read and `manage` to write. A device's
own running texts SHALL be governed by the menu that owns that device's display
kind.

#### Scenario: Write with only view grant

- **WHEN** a caller holding only `view` on `running-text` attempts to create a running text
- **THEN** the API SHALL respond 403

#### Scenario: Device texts governed by the device's display menu

- **WHEN** a caller lacking a grant on a device's display menu attempts to configure that device's running texts
- **THEN** the API SHALL respond 403

#### Scenario: A device session cannot write

- **WHEN** a device session attempts any mutation of running texts or sounds
- **THEN** the API SHALL respond 403
